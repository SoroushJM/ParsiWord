# Word Android: second reproduction, 2026-10-21

The user's second screenshot disproves the proposed 0.2 direction fix. Both Persian-only parentheses and mixed Persian/Latin parentheses are broken in **Microsoft Word for Android**. Standalone English paragraphs are now LTR, which is useful but insufficient. Font downloading, Tailwind and shadcn are unrelated to this bug.

The current `converter.ts` splits Persian text at every neutral character, tagging only strong RTL letters and their combining/joining characters with `w:rtl`. Persian spaces and parentheses consequently have no explicit RTL characteristics. Microsoft's `w:rtl` specification permits contextual overrides for neutral characters; avoiding those overrides universally is not a valid general solution. Conversely, deriving every `w:rtl` value from resolved UAX #9 levels breaks numeric/Latin groups such as `250 USD`. These are different concerns: contextual grouping, Unicode embedding, and Word run formatting.

The same v0.2 document was converted to PDF with the installed LibreOffice headless wrapper. Its Persian parentheses look correct there, despite the user's real Word screenshot showing failures. Currency appears as `USD 250` instead of the intended Latin phrase `250 USD`. A LibreOffice-only visual result cannot certify Android Word behavior. DOCX XML structure tests cannot do so either.

## Research after device results: simplify the strategy

The user explicitly asked for research into a broader, simpler fix rather than a parentheses-specific workaround. Primary sources confirm that this is a general contextual direction problem:

- [Microsoft: bidirectional support](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/user-interface/bidirectional-support#issue-ltr-text-combined-with-neutral-characters-in-rtl-input) documents the very similar `Dynamics (DAT)` example. The same article discusses underscores, hyphens, phone numbers and numerical identifiers. It explains that Word stores higher-level contextual information which plain Unicode text alone does not contain.
- [Microsoft: w:rtl](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.righttolefttext#remarks) explicitly shows Arabic words and their intervening space carrying `w:rtl`, and permits joining them into one run. It forbids applying RTL to strongly LTR text. The v0.2 invariant "never mark spaces or punctuation RTL" was our implementation mistake, not a Word requirement.
- [Pandoc's DOCX writer](https://github.com/jgm/pandoc/blob/main/src/Text/Pandoc/Writers/Docx/OpenXML.hs#L1269-L1295) uses ordinary `w:bidi` and `w:rtl` properties according to directional context, removing them when leaving that context. This code does not automatically infer arbitrary semantic phrases; it is a reference for serialization, not proof that Pandoc solves every mixed-text ambiguity.
- [W3C: inline bidirectional text](https://www.w3.org/International/articles/inline-bidi-markup/index.en) recommends tight grouping of entire opposite-direction phrases, including their own punctuation. Its HTML markup is not DOCX markup; the grouping principle is applicable. Unicode marks have specific uses, rather than being a default substitution for correct directional structure.
- [Microsoft: RtlRun](https://learn.microsoft.com/en-us/office/vba/api/word.selection.rtlrun) sets run reading direction and can affect paragraph alignment. It is not an automatic detector of Latin phrases or user intent.

Recommended implementation direction: A's ordinary Word properties and complete contextual phrases as the base. Keep Persian spaces and punctuation with Persian context; keep complete Latin expressions, URLs, identifiers, and their own punctuation in LTR context. Intersect those contexts with formatting/hyperlink boundaries without changing logical character order. Do not introduce B's nested embeddings. Use C's small LRM assistance only where tests establish it is needed, such as a numeric/Latin phrase that otherwise reorders in a supported reader. A is sufficient for the visible phone fixtures, whereas the existing LibreOffice comparison shows a currency difference; do not silently dismiss that evidence.

There is no single unconditional global RTL switch which both satisfies the `w:rtl` specification and correctly handles all strong Latin text. There is also no universally correct intent for every ambiguous plain-text number or punctuation group. Keep the implementation small, use standard properties, and test a broader corpus before claiming a general fix. No converter change or new APK was made during this research request.

## User's OpenEdition reference after 0.2.1

The user clarified that their original RtlRun request referred to the Word ribbon customization workflow shown in [OpenEdition, Styling a text as RTL](https://documentation.openedition.org/en/docs/14-styling-a-text-as-rtl/), and supplied a screenshot. The visible screenshot explains adding Right-to-Left / Left-to-Right commands from All Commands on Windows and macOS. Full article access was denied by the site's Anubis bot filter through both the web tool and an ordinary Chromium navigation; do not claim to have read the full page or identify its exact command solely from the translated labels in the screenshot.

Independent Microsoft primary sources distinguish three built-in commands: RightPara (0x003C), RtlPara (0x041F), RtlRun (0x0422). [MS-DOC Fci](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/e86aecb4-bb67-4de2-9b06-37771115f274) describes them respectively as paragraph alignment, paragraph orientation and making the current run RTL. [Selection.RtlRun](https://learn.microsoft.com/en-us/office/vba/api/word.selection.rtlrun) specifies reading direction of the selected run and conditional paragraph alignment changes. This supports the user's distinction between alignment and run reading direction.

The app currently sets paragraph and contextual run properties separately. Those features must not be claimed to be an experimentally verified reproduction of Word's RtlRun command: no Microsoft Word desktop instance has executed that command and saved a before/after document here. The exact serialized effect of that command in mixed text remains unverified. A before/after DOCX comparison in actual Word would establish the mapping. This clarification changes the research record; it does not establish a new failure in 0.2.1, and no replacement APK was built in response to the link.
