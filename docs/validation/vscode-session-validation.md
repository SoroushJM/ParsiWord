# اعتبارسنجی نشست و نماهای VS Code

اجرا در ۲۰۲۶-۱۰-۲۳ با VS Code 1.143.1 واقعی روی Windows و webview تولیدی انجام شد؛ نتیجهٔ نهایی ۳۱ بررسی پذیرفته است. فرمان بازاجرا `pnpm run test:vscode` است. گزارش ماشین‌خوان، رنگ‌های محاسبه‌شده و وضعیت نما در `artifacts/vscode-test/results.json`، تصاویر بالای پوسته در `shell-vscode-*.png`، محتوای سند در `theme-vscode-*.png` و سه نمای باریک در `narrow-*.png` همان پوشه ثبت می‌شوند. این شاهد اجرای بومی VS Code است؛ نه شاهد اجرای Android.

آزمون خطای اولیه در `artifacts/vscode-test/delayed-ack-before.json` نشان داد Save می‌توانست tail محلی را هنگام تأخیر واقعی ack قبلی جا بیندازد. runner فقط در محیط آزمون تحویل ack میزبان را ۱۵۰۰ میلی‌ثانیه عقب می‌اندازد؛ صف TextDocument مسدود نمی‌شود. نسخهٔ اصلاح‌شده هم Save در webview و هم File Save بومی را با tail کامل روی دیسک می‌سنجد. درخواست نامعتبر پاسخ خطای صریح دارد و لغو Save بومی به‌صورت موفقیت گزارش نمی‌شود.

سه شناسهٔ editor از یک مجموعهٔ نشست‌ها و صف‌های مشترک برای هر URI در extension استفاده می‌کنند. نمای Source همان textarea فارسی ParsiWord است؛ نمای Rendered همان rich editor قابل‌ویرایش است. تغییر منبع، rich editing، Undo/Redo بومی، تغییر هم‌زمان دو نما و تغییر فایل روی دیسک روی همان TextDocument آزمایش شدند. native Text Editor، Outline، پیوندهای Markdown، preview بومی و Git diff همچنان جدا قابل استفاده‌اند.

تست IME هر دو ترتیب `compositionend → input` و `input → compositionend` را با دقیقاً یک تغییر بومی نهایی بررسی می‌کند. رسیدن ack واقعی تأخیردار همراه با تغییر بومی غیرمتداخل، متن در حال composition را جایگزین نمی‌کند. تغییر متداخل، متن کامل پایان composition را در سند بازیابیِ ذخیره‌نشده نگه می‌دارد. این‌ها ترتیب رویدادهای مرورگر را در webview واقعی اجرا می‌کنند؛ ادعای آزمون صفحه‌کلید فیزیکی یا IME سیستم‌عامل ندارند.

هنگام بستن editor سفارشیِ dirty، VS Code می‌تواند پیش از dispose مدل بومی را به متن ذخیره‌شده برگرداند. در این حالت replay یک patch کوچک ممکن است بخش قبلاً اعمال‌شدهٔ draft را از دست بدهد. مسیر dispose وقتی baseline بومی تغییر کرده باشد، draft کامل را در سند بازیابی باز می‌کند. آزمون reopen وجود متن کامل در TextDocument یا سند بازیابی دقیق را الزام می‌کند؛ ادعای انتقال بی‌درنگ و بدون recovery ندارد. journal معمولی فقط tailهای افزایشی را می‌فرستد و یک نسخهٔ کامل اضافه به‌ازای هر keystroke نگه نمی‌دارد.

حالت source-only و rendered-only با صفحه اسکرول می‌شوند. در آزمون نگه‌داشتن همان source view و نمایش دوبارهٔ آن، selection برابر ۷ تا ۱۳ و `scrollY=120` باقی ماند. پس از dispose آن و ساخت rendered view با شناسهٔ editor دیگر، textarea پنهان با selection صفر و صفحه با `scrollY=0` آغاز شد. انتقال caret یا موقعیت اسکرول میان دو نوع editor پیاده نشده است؛ نگه‌داشتن همان webview را نباید با ساخت webview جدید یکسان دانست.

سند بومی بیرونیِ ۵۰۰٬۰۲۰ نویسه‌ای کامل در source recovery دیده شد، ابتدا به ۵۰۰٬۰۱۰ و سپس به متن زیر حد کاهش یافت. CRLF بومی با ویرایش حداقلی حفظ شد. آزمون مرورگر جدا در `tests/document-session.spec.ts` بازیابی و export کامل draft بزرگ در موبایل و گرفتن snapshot متن و تنظیمات در همان task پیش از await فونت را بررسی می‌کند. دو regression جدید با متوقف‌کردن timerهای نمایشی ثابت می‌کنند جابه‌جایی فوری منبع/rich و کلیک ابزار rich در دسکتاپ آخرین منبع را پیش از transaction بعدی می‌گیرند؛ تایمرهای ۲۰۰ و ۱۲۰ میلی‌ثانیه فقط هنگام ماندن در همان ویرایشگر برقرارند.

بازاجرای suite موجود یک regression مهاجرت تنظیمات را آشکار کرد: draft قدیمی با `alignmentOnly:true` نباید گزینهٔ مقایسهٔ حذف‌شده را دوباره وارد خروجی کند. normalizer مشترک اکنون مانند مبنا این مقدار را هنگام بارگذاری خاموش می‌کند؛ متن، title، RTL و مهاجرت Arial به Vazirmatn حفظ می‌شوند. شش آزمون واحد و همان آزمون مرورگر قدیمیِ export، بدون تغییر انتظار `<w:bidi/>`، پاس شدند. API مستقیم converter برای مصرف‌کنندهٔ سازگار همچنان گزینهٔ صریح خودش را می‌پذیرد.

در چهار تم واقعی Light، Dark، High Contrast و High Contrast Light، پس‌زمینهٔ هر دو بوم، پیوند، caret و focus با tokenهای میزبان برابر بودند. نسبت کنتراست متن منبع و rich به‌ترتیب ۱۱٫۲۰، ۱۰٫۲۶، ۲۱ و ۱۴٫۵۵ و نسبت پیوند ۶٫۳۱، ۶٫۶۵، ۷٫۹۶ و ۸٫۹۸ بود. تغییر تم منبع را عوض نکرد. خروجی Word با متن/فرمول قابل‌ویرایش، فونت جاسازی‌شده و تصویر نمودار، Markdown کامل و PDF با متن قابل جست‌وجو نیز از همان webview ساخته و بررسی شدند.

پس از اصلاح پوسته، marker بومی در هر چهار تغییر واقعی تم باقی ماند؛ فونت و اندازهٔ UI با token میزبان برابر، card بدون radius/shadow و دکمه‌های فرمان ۲۶px بودند. فونت منبع Vazirmatn/Tahoma و فونت سند rich همچنان مستقل ماند. کنتراست KaTeX به‌ترتیب ۱۱٫۲۰، ۱۰٫۲۶، ۲۱ و ۱۴٫۵۵ و آیکن تیتر pane نسبت به زمینهٔ خودش ۵٫۹۴، ۷٫۱۶، ۷٫۰۱ و ۸٫۹۸ اندازه‌گیری شد. focus مؤثر textarea روی container آن با رنگ focusBorder دیده شد؛ ضخامت یک‌پیکسل CSS در scale بومی ۱۲۵٪ به ۰٫۸px گرد شد. تصویر Mermaid پالت روشن ذاتیِ خوانا دارد و ادعای dark بودن خود تصویر ندارد.

عرض واقعی webview برای هر سه mode برابر ۴۰۰px و ارتفاع ۷۸۲px بود؛ عرض سند از viewport بیشتر نبود. آزمون با Tab واقعی، تمام دکمه‌های فعال toolbar را پیمود: combined برابر ۲۰، source برابر ۵ و rendered برابر ۱۵. یک دکمهٔ rich ابتدا فقط جزئی دیده می‌شد؛ focus بومی اکنون خود control را با scroll نزدیک در همان نوار کاملاً نمایان می‌کند. سه تصویر باریک و تصاویر Dark/HC بازبینی دیداری شدند. اعلان بازیابی پایین تصاویر باریک حاصل fixture عمدیِ conflict قبلی در همین suite است.

بازبینی مستقل بعدی یک ضعف جدا در syntax منبعِ HC Light یافت: `textPreformat.foreground` میزبان سفید بود و math/code روی زمینهٔ سفید نسبت کنتراست ۱ داشتند، با اینکه متن کامل موجود بود. شاهد بومی محدود `PARSIWORD_TEST_THEME_WITNESS=hc-light-before` آن را ثبت کرد؛ پس از استفاده از editor.foreground در tokenهای source تم‌های کنتراست، شاهد `hc-light-after` همهٔ این spanها را با نسبت ۱۴٫۵۵ و برابری دقیق source/overlay پاس کرد. JSON و تصویر هر دو شاهد در `syntax-hc-light-{before,after}.*` نگه‌داری شدند. فقط همین شاهد کوتاه پس از اصلاح CSS بازاجرا شد، نه همهٔ ۳۱ بررسی. حلقهٔ عادی چهار تم نیز اکنون assertion غیرتهیِ contrast برای math/code منبع دارد تا بازگشت این ایراد را بگیرد.
