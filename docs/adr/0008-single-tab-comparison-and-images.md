# مقایسهٔ یک‌تب، چهار نمای تغییرات و تصاویر Markdown

کاربر چیدمان قبلی یک‌تب را به دو گروه جدا ترجیح می‌دهد و هر دو نوع محتوا، یعنی منبع Markdown و خروجی رندرشده، را با هر دو چیدمان کنارهم و Inline می‌خواهد. رابط RTL پارسی‌ورد، پوستهٔ فشردهٔ موجود در تاریخچهٔ Git و تاریخچهٔ بومی سند باید حفظ شوند. بازسازی رابط از روی تصویر یا جایگزینی آن با ادیتور بومی، تصمیم پذیرفته‌شده نیست.

یک `CustomTextEditorProvider` عادی با شناسهٔ `parsiword.markdown.diff` سند سمت جدید را نگه می‌دارد. هر دو سمت داخل همان Webview رندر می‌شوند؛ جابه‌جایی، بستن و بازکردن تب به کل مقایسه مربوط است. نسخهٔ قدیمی فقط‌خواندنی است. فایل فعلی همان TextDocument، pending journal، ذخیره و Undo/Redo بومی را دارد؛ تاریخچهٔ دوم یا ادیتور مخفی ساخته نمی‌شود. wrapper قدیمی Source Control به این تب تبدیل می‌شود. این مسیر به API پیشنهادی `customEditorDiffs` وابسته نیست.

نام فایل و فرمان‌های وبی «باز کردن فایل» و «یادداشت تازه» از رابط داخل افزونه حذف می‌شوند؛ خود VS Code این‌ها را مدیریت می‌کند. خروجی Word/PDF/Markdown و تنظیمات نمایش در کنترل‌های فشرده باقی می‌مانند و در مقایسه داخل همان هدر مشترک قرار می‌گیرند. چیدمان و فاصله‌های معمول از utilityهای Tailwind استفاده می‌کنند؛ CSS اختصاصی برای تم میزبان و رفتار ویرایشگر باقی می‌ماند و ابعاد ثابت با `rem` نوشته می‌شوند.

ارتفاع هدر و نوار قالب‌بندی دو طرف و فاصلهٔ شروع محتوا هماهنگ‌اند؛ جداکننده با ماوس و صفحه‌کلید عرض دو سمت را تغییر می‌دهد. اسکرول کنارهم در هر دو جهت همگام می‌شود و محل متناظر منبع را با اختلاف نسخه‌ها و شکست سطرها تطبیق می‌دهد. تنظیمات فونت، اندازه و جهت، بین هر دو سمت و مرور Inline مشترک‌اند و متن نسخهٔ قدیمی را تغییر نمی‌دهند.

در چیدمان کنارهم، نسخهٔ فعلی مستقیماً از منبع یا خروجی قالب‌بندی‌شده ویرایش می‌شود. Inline یک جریان مرور شامل محتوای مشترک و حذف‌ها/اضافه‌ها به ترتیب سند است. برای ویرایش در Inline، «ویرایش نسخهٔ فعلی» همان ادیتور و همان تاریخچه را در همان تب آشکار می‌کند؛ «مرور تغییرات» نتیجه را برمی‌گرداند. بلوک‌های حذف‌شده ورودی قابل‌ویرایش نیستند. جست‌وجو یا رفتن به خط در مرور Inline، نمای نسخهٔ فعلی را آشکار می‌کند. staging تکه‌های تغییر همچنان متعلق به مقایسه‌گر بومی Git است.

مسیرهای تصویر در پیش‌نمایش، بدون تغییر دادن Markdown اصلی نمایش داده می‌شوند. میزبان VS Code مسیر نسبی را نسبت به سند resolve می‌کند و منابع محلی را از محدودهٔ سند/پروژه از مسیر Webview می‌دهد. نسخهٔ قدیمی از مسیر سند قدیمی استفاده می‌کند؛ باینری تصویر از فایل فعلی خوانده می‌شود و مقایسهٔ تاریخچهٔ باینری تصویر در این تصمیم نیست. خطای بارگیری با متن جایگزین نمایش داده می‌شود.

در سایت، «پوشهٔ پایهٔ تصاویر» یک پوشهٔ انتخاب‌شدهٔ محلی و یک مسیر اختیاری زیرپوشه برای محل سند می‌گیرد. نوشتن مسیر دلخواه در دیسک، مجوز خواندن به مرورگر نمی‌دهد؛ انتخاب پوشه، مجوز واقعی را فراهم می‌کند. فایل‌ها آپلود نمی‌شوند. مسیرهای `../` فقط داخل پوشهٔ انتخاب‌شده resolve می‌شوند. انتخاب پوشه متعلق به همان صفحه است و URLهای موقت هنگام پاک‌کردن، انتخاب مجدد یا خروج آزاد می‌شوند. تصویرهای آنلاین و تصویرهای reference-style نیز پشتیبانی می‌شوند. دامنهٔ اولیهٔ این تصمیم نمایش تصاویر بود؛ درخواست بعدی کاربر جاسازی واقعی آن‌ها در Word/PDF را هم اضافه کرد و در [راهنمای خروجی](../pdf-export.md) ثبت شده است.

دامنهٔ میان‌برهای تأییدشده در [تصمیم ۰۰۰۷](0007-vscode-ui-history-and-shortcuts.md) حفظ می‌شود. آزمون باید یک تب واقعی، چهار نمای مقایسه، Undo/Redo واقعی با وجود سند نامرتبط دارای تاریخچه، ذخیرهٔ بایت‌های درست، فقط‌خواندنی بودن نسخهٔ Git، نمایش تصویر، تنظیمات مشترک و هم‌ترازی هدرها را بررسی کند. آزمون مرورگر وب باید انتخاب/تعویض پوشه و مسیر زیرپوشه را با فایل واقعی بررسی کند.
